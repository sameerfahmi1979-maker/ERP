# Communications spending controls

The current release configuration is **off**. A backend deployment or a new budget approval does not start a provider or a dispatcher. The existing ERP runtime is metered. The project has no verified independent bound for additional Railway cost, Cloudflare SFU shutdown exposure or the recurring liability of indefinitely retained history. No production meter, owner binding, spending authority, monitoring recipient, service credential or continuing-retention proof is included in the migration.

## Server configuration

The environment switches below are independent. Each accepts only the exact text `true`. An omitted, blank or unrecognized value keeps the feature off. These are server settings. No application bundle or client preference can grant admission.

| Work | Setting |
| --- | --- |
| Ordinary chat commands | `ERP_COMM_CHAT_ENABLED` |
| Communication presence and Realtime | `ERP_COMM_REALTIME_ENABLED` |
| Retained media upload | `ERP_COMM_MEDIA_UPLOAD_ENABLED` |
| Media downloads | `ERP_COMM_MEDIA_DOWNLOAD_ENABLED` |
| Exports | `ERP_COMM_EXPORT_ENABLED` |
| Android push dispatch | `ERP_COMM_PUSH_ENABLED` |

| PTT history/replay delivery | `ERP_COMM_PTT_REPLAY_ENABLED` |
| SOS transport | `ERP_COMM_SOS_ENABLED` |

Changing a flag alone cannot admit work. Keep the credential and service-specific configuration separate. The installed cost scope is `communications`. The public operator API rejects invented scopes. Existing ERP notification, DMS and HR functions use their existing controls.

## Calling and consuming a permit

Call `reserveCommunicationBudget` before each independently metered operation. Supply a server-derived actor/profile ID, cost scope, unique operation ID, feature, a conservative integer USD-micro floor and the end of all liability. A zero floor still requires every protected database proof. A null deadline signals continuing retention, which requires documented zero-additional-cost storage after expiry of a finite grant. ERP chat and retained uploads also require this proof where conservative feature-level accounting includes retained history. Push requires both ERP runtime/database and FCM evidence. Live PTT requires runtime/database and shared SFU/TURN evidence. Reserve every additional fan-out, upload stage, issuance, playback and export path that independently consumes a resource.

For authenticated SQL operations pass `binding: {actorSessionId, command}`. The server then forwards the opaque permit to the feature SQL handler. That handler computes its feature/scope and current ERP profile from trusted context, removes the injected permit envelope field and calls `erp_comm_cost.take_permit(permit,feature,scope,profile,command)` **inside the same transaction** as the effect. A trusted security-definer service RPC may call `take_service_permit(permit,feature,scope,profile,session,command)` with its verified original actor/session. Neither helper is executable directly by client roles. Exact canonical JSON, session, active ERP identity, permit expiry, current owner/approval, unit slots and pause are checked. The permit may be consumed once. A failed business transaction rolls consumption back. The feature still enforces its independent membership, access, device and business idempotency rules.

Retry an ambiguous reservation RPC with the same reservation ID and fields. Preserve the semantic mutation ID in the business command. A new billable delivery/response attempt needs a fresh reservation, including an idempotent read of a prior result. The trusted sender should use a provider idempotency mechanism or reconcile an ambiguous external effect before retry. A local SQL commit cannot establish that an external service transmitted, stopped or billed a particular amount. Immediate revocation of ongoing media depends on a verified stop protocol and already-reserved shutdown budget.

An unsuccessful reservation returns `{ok:false,status:503,reason}`. Clients can distinguish unavailable evidence, absent owner, default-off, exhaustion, scope pause, expired approval or stale meters. Suppress automatic retry storms and budget-dependent tasks until prerequisites recover. Cleanup, cancellation and trusted settlement may run after the feature switch is off using reserved resources. A timeout never releases held money or capacity.

## Persistent evidence and funding

The private `erp_comm_cost` schema has no client table grants. The operator RPC uses the actual ERP user session. Reservation, settlement, pause and bounded cleanup use a transactional service-role RPC. Feature code and monitoring roles have no direct write path to owner enrollment, proof, meter, capacity or final-provider-evidence tables.

1. Enroll an independently verified ERP owner in the singleton authority row using a reviewed administrative change with evidence. Installation leaves this binding empty. The public interface cannot self-enroll, transfer ownership or promote an administrator into the owner.
2. A trusted billing evidence collector must establish each applicable resource unit, billing account, period, net available quantity, complete meter observations and a guaranteed upper bound through final shutdown. Include non-feature usage, active sessions, unseen consumption, retained objects, existing commitments, billing rounding and tax where applicable. Source rate cards and delayed dashboards alone cannot establish these bounds. Use one stable capacity slot per billing account, dimension and resource unit. The physical unit ceiling is shared by all matching approvals and features.
3. For a single exact operation, record the trusted proof and bounded meter rows. A standing envelope may reference a protected template only when the bounds hold for **every** request of that feature, its maximum payload, recipients, retries, time, length and failure modes. Under a global ledger lock the RPC checks the snapshot, required dimensions, freshness, available units and remaining approved money, and records money and physical units atomically. The operation receives its own immutable-at-issuance copy of standing evidence. No standing envelope is installed. The unit ledger consumes its conservative upper bound and does not automatically release previously allocated units or roll over when an invoice resets. A future protected reconciliation process must prove availability across billing windows before raising a ceiling.
4. Money is stored as nonnegative exact integers in millionths of one USD. A positive increment or monetary safety margin requires a matching active owner-approved cap. A valid zero-increment proof can admit work after owner enrollment without a spending grant. Keep all associated usage within the explicit physical envelope. Accepted indefinite storage needs independent continuing-retention evidence even when a paid period is active.
5. When actual cost is final, an independent collector supplies final evidence bound to the opaque permit. Call `reconcileCommunicationBudget` with that exact evidence ID and amount. A confirmed never-started operation can settle at zero. Uncertain settlement keeps the reservation. An overrun records the full actual charge, pauses new work for the affected communications feature/scope and enqueues an alert. No whole-workspace stop, replica reduction, cloud plan change or deletion of retained data is performed.
6. Use `pauseCommunicationBudget` for a trusted internal incident, or the authorized operator command for a human pause. Gate changes reject future reservations. A durable pause also fences still-unconsumed user SQL permits. Already-issued provider capabilities, signed downloads and active transfers require bounded termination/accounting. Resumption is a separate reviewed change following evidence/rate review.

## Cleanup funded before admission

For a provider session or partial upload, the originating proof must include the shutdown cost in its monetary and unit ceilings. The private cleanup limit also records the allowed endpoint, maximum distinct resource IDs and a finite attempt count per resource. Live PTT requires a track-close allowance. An upload requires partial-object cleanup. A TURN grant needs its own revoke allowance before issuance.

Call `bindCommunicationCleanupResource` with the original permit, deterministic resource ID and the narrowly defined endpoint before remote creation. Allowed endpoints are `close_sfu_tracks`, `revoke_turn` and `discard_partial_upload`. A service worker calls `authorizeCommunicationCleanup` with that same binding and a unique attempt ID. Duplicate IDs return the existing attempt. The worker checks provider state on ambiguous outcomes and calls `confirmCommunicationCleanup` only after termination or staged-object removal is confirmed. An unconfirmed resource holds final settlement. No fresh admission, current meter or renewed spending approval is necessary for this previously reserved cleanup. It cannot authorize a new track, download, upload, notification or removal of accepted history. A known bound on termination despite control loss is still required before activation.

A new SOS has a separate original-incident envelope. `erp_comm_cost.require_sos_envelope(permit,recipient_count,device_count)` requires that the exact user permit has been consumed in the same originating database transaction. The incident records its actual eligible audience and device counts within protected ceilings, and may cancel exactly once against that original audience. Indefinite retention and the ability to record a later cancellation with zero additional cost after approval expiry each require independent evidence. The cancellation control may append its narrow status entry during a pause. It does not grant general push transport or establish that a device received the cancellation. An FCM delivery attempt requires its own bounded dispatch policy.

## Authenticated operator commands

All public commands use the existing ERP communications API and the `communications` scope. The UI must render only controls authorized by the returned capabilities. SQL independently authenticates the actor and session. Ordinary accounts receive a generic controlled-status response.

| Command | Inputs and result |
| --- | --- |
| `budget.status` | `scope`. Returns `canApprove`, `canMonitor` and held reasons. Authorized monitoring users also see active approval, spent/reserved amounts as decimal strings, paused features and server-disabled features. The presence of a standing template is insufficient to establish per-operation admission. |
| `budget.approve` | `scope,features,currency:"USD",maxMicros,endsAt,clientMutationId`. The cap is a positive decimal integer string. Use an absolute UTC end instant and UUID mutation ID. Only the bound owner with a recently authenticated ERP session can approve. A billing cycle never renews the grant. One outstanding approval prevents accidental stacking. |
| `budget.revoke` | `scope,approvalId,clientMutationId`. Only the bound, freshly authenticated owner can revoke. Existing financial obligations remain booked. |
| `budget.pause` | `scope,feature,reason,clientMutationId`. Owner or a currently selected technical recipient may pause the communications feature. |
| `budget.monitor` | `scope` lists the selected technical recipients by exact ERP profile IDs. To replace them, the freshly authenticated owner supplies `recipientProfileIds` as decimal strings and `clientMutationId`. The owner is always an additional alert recipient. Empty selection removes the optional recipients. |

Changed arguments under the same mutation ID are rejected. The SQL authority checks a current ERP session and an AMR timestamp no older than five minutes for a qualifying interactive method. A refreshed token alone cannot issue an approval. Public responses use ERP profile IDs. No user can add themselves to monitoring via a Global Admin role.

The service-only feed `erp_comm_budget_monitor_events(p_after,p_take)` reads up to 100 existing events after an integer cursor using the current recipients’ indexed event histories. Admission records an early warning at 80% of the fixed cap and records exhaustion. A separately prepaid notification tick can project one near-expiry or expired notice for one current recipient. The tick is single-use, including when there is no due work. Consumers must persist cursor/delivery state, recheck selected recipients, deduplicate by event ID and target the ERP notification center and Android push only when permitted. Push failure or disabled push must remain visible in ERP.

## Retention and funded controls after a pause

Every admitted work item creates durable accounting records. A Realtime presence pulse therefore needs documented continuing zero-increment storage and a positive `permanent_ledger_bytes` allocation in the database capacity ledger. The SQL floor grows with the recorded proof, meter rows, permitted cleanup attempts and maximum SOS audience. Independently measured indexes, WAL, backups and future retention must also fit the recorded upper bound. No billing or semantic idempotency record is silently deleted to make this check pass.

Protected finite control pools reserve a dedicated permit for one subject and one purpose. Each pool requires a physical `funded_<purpose>_actions` unit, continuing zero-increment evidence and an additional permanent ledger byte allowance. Enrollment consumes the canonical `budget.fundControl` permit and pins the maximum, subject, purpose and ending instant. The pool starts disabled unless explicitly configured. Issuing new work requires a funded independent read and push allowance for the owner and each selected alert recipient. Commissioning the exact protected alert pool is the narrow bootstrap exception. An approved spending amount on its own creates no provider capacity.

Budget alerts use separate read and push shares so operator reads cannot consume all delivery attempts. The worker must validate the protected source, active account, device, job and lease before both preparation and dispatch. The pre-funded continuation does not consult the paused general chat or push budget. FCM still requires its own explicit control-transport activation, server sender credential and functioning provider. No SQL receipt proves delivery.

An original SOS binds its finite audience to its admission permit in the effect transaction. A cancellation binds a single new event against those original recipients. Each phase is limited to the approved device count and retry/read allowances. Current membership, Off-duty, active phone/session, source and worker lease are still checked at dispatch. A control-only inbox may show up to sixteen eligible budget/SOS events, with a pre-funded one-use read. An empty pool results in a held outcome visible through the control status. Separate report, block and terms allowances continue only for enrolled profiles with remaining purpose-specific capacity. Repeated semantic no-ops need no new durable receipt.

A chat stage binds its immutable Storage identifier, a minimum of three cleanup attempts, a finite recovered-worker schedule, and capacity through the entire stage period plus the cleanup tail before the blob write. A funded worker poll may execute once and stops when its proof, horizon or finite poll balance is unavailable. Stage admission reserves against the active worker backlog. Confirmed deletion completes cleanup; atomic acceptance of the exact verified original into permanent history records a distinct retained handoff and blocks later deletion claims. An already-issued cleanup attempt prevents the retained handoff.

Exports require a separate Railway `encrypted_spool_byte_hours` reservation and protected spool evidence covering maximum volumes, slots and bytes per slot, key destruction, cleanup/restart delay and ciphertext lifetime. A delayed idle cleanup that outlives all verified guarantees prevents admission.

A PTT worker also needs a finite fleet plan and prepaid per-worker poll capacity. The plan records the total allowed boots, active replica limit, pessimistic busy-tick duration, restart delay, hard expiry and independent operating evidence. A process starts with a new fenced boot ID, a local poll cap and absolute local cutoff. Its effective horizon is the minimum of those limits and its protected pool/fleet limits. The process stops polling on refusal or unknown outcome. A new live resource needs enough remaining ticks and wall time to drain all outstanding reservations at the verified worst-case rate. An idle, unbounded one-second polling interval cannot be activated. No workers, fleet entries or billing metrics are supplied by installing this schema.

For the notification scheduler, the only admitted scheduler subject is `mobile-notifications`. Its protected `notification_tick` pool includes the bounded number of wakeups and funded retirement. The last usable tick returns a cutoff at the current time. The scheduler must then unschedule without dispatching more work. No recurring database job is installed or funded by this budget package.

SOS inbox discovery reserves two recipient slots at origination, including the future cancellation slot. The configured `sos_discovery_target_checks` unit bounds current entitlement lookups across positive read balances. Each read selects an eligible source with remaining credits before applying the inbox page limit. Historical exhausted or revoked sources cannot hide an eligible funded event. A recipient at their protected discovery ceiling cannot receive a newly allocated origin until a slot becomes available.

Before new PTT effects, the drain calculation starts at the latest possible cleanup-ready instant across admitted resources and ends by their earliest funded stop. Each outstanding attempt includes busy time, poll cadence and retry delay of at least 60 seconds. The calculation also includes the remaining heartbeat fence and restart delay. A recovery boot and its pool capacity must remain available for each worker with an outstanding drain obligation. The physical fleet and provider shutdown guarantees still require deployment-specific evidence.

## Recording and variable-size command effects

A floor press must snapshot every current recipient membership episode under the PTT membership lock. Before creating the lease or its child rows, `ptt_receipt_scan_limit` bounds a lookup to the funded ceiling plus one rejection probe. `require_ptt_receipt_capacity` binds the actual count and preassigned lease ID to the authenticated, consumed press permit in the same transaction. The per-operation protected `ptt_receipt_limit` and four physical database units cover the recording, every episode receipt, and up to one deferred Busy inbox and active-phone job per episode. The units are `funded_ptt_receipt_episodes`, `funded_ptt_busy_inboxes`, `funded_ptt_busy_device_jobs` and `ptt_floor_retained_bytes`. Base and per-episode byte bounds must include real indexes, backup and continuous retention. A channel may have more than 100 recipients. Insufficient funding holds the floor press.

Other commands with variable-sized effects bind a protected `effect_limit` to an exact command name and class. The `effect_<class>_items` and `effect_<class>_bytes` units must include the complete measured database work for a single effect, its rejection probe, receipt, durable children and response or deferred obligations. `effect_scan_limit` bounds the caller’s snapshot. `claim_effect` checks the actual or conservative upper count and uses the class once per consumed permit. Both require the authenticated actor, active transaction, session and full original command. The collector or commissioning process must include all relevant additional provider dimensions in the original money/unit reservation.

## Worker registration and chat-stage recovery

Railway currently has no mounted volume in the inspected environment. The worker proof uses an independently verified finite host configuration and prepaid Supabase records. A protected `worker_probe_plan` reserves the maximum number of original, failed, denied and ambiguous starts across the fixed deployment set. Both Railway and database ledgers must hold `funded_worker_registration_probes` for at least replicas × (one plus permitted restarts per deployment) × maximum deployments, including manual starts and overlapping rollouts. The signed launch envelope carries the exact deployed instance’s deployment ID, worker/boot IDs, finite registration window, absolute stop, poll cap and evidence ID. An external commissioning authority must verify the genuine hosting and capacity evidence before signing. A changed deployment policy requires fresh funding and evidence. A disposable local path provides no cross-process protection.

The chat-stage registrar charges a preissued boot before first registration. A process uses a single admission attempt. The default-closed worker uses a 30-second idle interval. The protected fleet plan allows at least 70 seconds for each busy claim/Storage/confirmation sequence, 180 seconds for an abandoned claim lease, five seconds for registration, and a measured restart delay. Before staging, PostgreSQL compares all pending cleanup attempts against their latest possible ready time and earliest funded stop. Each possible failed attempt also needs a separately prepaid spare boot, registration window and poll limit sufficient to recover. The capture and poll paths hold if the physical recovery mechanism, network/commit tail or enduring containment remains unproven. The database does not create a host, worker, volume or recovery scheduler.

An offline commissioner uses the actual deployed Railway ID. It records the protected financial plan and immutable `worker_launch_ticket`, then calls private `erp_comm_cost.take_worker_delivery(boot,attempt)`. The commissioner must commit the returned strict v1 receipt before signing its exact UTF-8 JSON bytes and making a single launch POST. A refused or ambiguous result retires that attempt. Probe pricing must cover commissioner calls, signature delivery, rejected HTTP/RPC probes, response loss, host and database work. The CLI and target may use only the separately approved fixed deployment and usage envelope. The application has no permission to issue or sign a receipt. A manual launch receipt alone provides no measured recovery guarantee. A separate `worker_probe_plan.recovery_seconds` and `recovery_evidence`, current across the entire obligation and affordable within the fleet’s restart time, are mandatory for new chat stages and PTT effects. All corresponding production fields start empty.
